# Diabetes Risk Check

A Flask app that estimates diabetes risk from a few simple inputs, explains
what drove the result, and lets signed-in users track their checks over time.
Trained on the Pima Indians Diabetes dataset (768 women, aged 21+).

> Educational project. The score is a model output, not a diagnosis.

## What's in it

- **Accounts**: register, sign in, sign out. Hashed passwords, CSRF protection,
  account lockout after 5 wrong passwords, safe `next` redirects.
- **Risk check**: BMI calculator, lifestyle sliders that estimate glucose and
  blood pressure (or enter your own readings), animated gauge and health score.
- **Explanation**: exact Shapley values show how much each factor raised or
  lowered your score compared with a typical person in the reference sample.
- **PDF report**: built in the browser with jsPDF, from the check page or any
  saved check on the dashboard.
- **Dashboard**: every check is saved (SQLite) with a trend chart; delete any time.
- **Models page**: cross-validated comparison of all trained models.

## Run it locally

```bash
python3 -m venv .venv && source .venv/bin/activate     # optional
pip install -r requirements.txt
python3 train_model.py        # trains the models (about 20 seconds)
python3 app.py                # http://127.0.0.1:5000
```

Sign-in is required for the check page and dashboard. Create an account at
`/register`. The models page is public.

Optional: `pip install xgboost` before training to add XGBoost to the comparison.

### Tests

```bash
pip install -r requirements-dev.txt
python3 -m pytest -q
```

## Docker

```bash
cp .env.example .env          # then set SECRET_KEY
docker compose up --build     # http://localhost:8000
```

The image trains the models during the build, so the pickles always match the
installed scikit-learn. The SQLite file lives on the `db-data` volume.

### Deploying

Set `SECRET_KEY` and `COOKIE_SECURE=1` (HTTPS). SQLite needs a persistent disk;
on hosts with an ephemeral filesystem (for example free tiers) accounts and
history are lost on redeploy. Use a persistent volume, or swap `db.py` for
Postgres.

## Configuration

| Variable        | Default              | Purpose                                      |
|-----------------|----------------------|----------------------------------------------|
| `SECRET_KEY`    | generated in `instance/` | Signs session cookies                    |
| `DATABASE_PATH` | `instance/app.db`    | SQLite file                                  |
| `COOKIE_SECURE` | `0`                  | Set `1` behind HTTPS                         |
| `HOST` / `PORT` | `127.0.0.1` / `5000` | Dev server address                           |
| `FLASK_DEBUG`   | off                  | `1` enables the debugger (never expose it)   |

## Structure

```
app.py              routes, validation, prediction, history API
auth.py             register / login / logout, CSRF, lockout
db.py               SQLite schema and connection
explain.py          exact Shapley values for the 8 features
ml_utils.py         feature list + preprocessing pipeline (shared)
train_model.py      trains and cross-validates the models
templates/          base, login, register, index, dashboard, models
static/css, js      styles and page scripts
data/diabetes.csv   Pima dataset (Outcome column = target)
models/             generated by train_model.py
tests/              pytest suite
```

## Notes on the model

- Zeros in Glucose, BloodPressure, SkinThickness, Insulin and BMI are treated
  as missing and imputed (KNN) inside the pipeline, using training data only.
- Class weights handle the ~65/35 class imbalance. Because of this the score is
  a model score, not a calibrated probability.
- The best model is chosen by 5-fold cross-validated ROC-AUC.
- Insulin and skin thickness are optional in the UI; blank values are imputed.
- Family history is a yes/no answer mapped to a typical low or high value of the
  dataset's pedigree function.
- The training data is only women of Pima heritage, so results for other groups
  are less reliable.
